# 网易云音乐工具箱（图形界面）

把「在线下载」和「NCM 解码」合成一个窗口，两页共用同一个音乐库目录。

```
双击 启动.bat          正常使用（无控制台窗口）
双击 启动-调试.bat      出问题时用，保留控制台显示报错
```

## 页签一：在线下载（支持批量）

**输入框是多行的，每行一个链接或 ID，可以混合类型**——单曲、专辑、歌单、歌手热门、电台、播客单集
全部可以混着贴，点「解析列表」合并成一个下载队列，再点「开始下载」。

```
347230                                    ← 单曲
https://music.163.com/#/album?id=32311    ← 整张专辑
https://music.163.com/#/playlist?id=xxx   ← 歌单
# 这行会被忽略（# 开头是注释）
```

- **导入文件**：点「导入文件…」载入一个 txt（每行一个链接），也可以直接把 .txt 拖进输入框。
- **去重做了两层**：同一个源用两种写法给两次，只解析一次；同一首歌出现在多个歌单里，只下一次。
- **纯单曲走批量接口**：一次请求 200 首，比逐首查询快一个数量级；专辑/歌单/歌手/电台则并发解析。
- **来源列**：列表里能看到每首来自哪个专辑/歌单；下载时各自落进自己的子文件夹，不会混在一起。
- **重试失败项**：一轮跑完后点这个按钮，只把失败的曲目挑出来重下，成功的不用再走一遍。
- **快捷键**：Ctrl+Enter = 解析列表。

- **音质**：8 档，从标准 128k 到超清母带。取不到所选音质会自动逐级降级，并在日志里说明。
- **登录（想下付费曲目/无损必填）**：网易云在「取播放地址」这一步是看登录态的。
  不带登录态时，付费曲目返回 `code -110（需要登录）`，免费曲目最高只能拿到 128k。

  界面上有三个入口，按可靠性排序：

  ### 方式一：网页登录（推荐，最稳）

  点 **「网页登录（自动取Cookie）」** → 浏览器打开官方登录页 → 在浏览器里正常登录
  （手机号、扫码、验证码都行）→ 窗口每 3 秒自动检测一次，检测到就自动填入并验证。

  原理：Chromium 系浏览器的 Cookie 存在 SQLite 里，值是 AES-256-GCM 加密的，
  主密钥在 `Local State` 里用 Windows DPAPI 保护（绑定当前 Windows 用户）。
  程序复制一份 cookie 库再解密，**只挑 163.com 的项，不碰其它站点，也不写回原文件**。

  > **注意：Edge 运行时会独占锁定 Cookie 数据库，读不了。**
  > 遇到这种情况窗口会直接提示你关掉 Edge 再点「立即读取」。
  > Chrome 实测可以在运行状态下读取，不用关。用哪个浏览器登录都行，程序会自动找。

  ### 方式二：扫码登录

  点 **「扫码登录」** → 用「网易云音乐」App 扫码并确认。

  > **目前这条路大概率失败。** 网易云的风控会对第三方客户端的扫码登录返回
  > **8821「请切换其他登录方式或升级新版本再试」** —— 你手机上会显示授权成功，
  > 但服务端拒绝把登录态交给这个客户端。窗口会明确显示风控提示，不会让你干等。
  > 代码里已按 api-enhanced 的做法把 `type` 从 1 改成 3（较新的客户端场景），
  > 如果仍然被拦，请改用方式一。

  ### 方式三：手动填 Cookie

  **MUSIC_U 是 HttpOnly 的，Console 里跑 `document.cookie` 看不到它**，所以要用下面两种方式之一
  （界面上的「说明」按钮里也有）：

  | 方式 | 步骤 |
  | --- | --- |
  | 推荐 | F12 → Application → Cookies → music.163.com → 复制 **MUSIC_U** 的 Value，直接粘进 Cookie 框 |
  | 整串 | F12 → Network → 点任一发往 music.163.com 的请求 → Request Headers → 复制整行 **Cookie** 的值 |

  只填 MUSIC_U 的值也行，程序会自动补成 `MUSIC_U=…`；整串（含换行）也能识别。

  **填完点「验证」**：会显示登录的昵称、会员类型，并**真的去取一次流**，直接告诉你到底能不能下付费曲目。
  三种结果：登录成功且取流正常（绿）／已登录但只能拿试听片段（橙，说明该曲权限不够）／Cookie 无效或过期（红）。

  Cookie 会与匿名客户端标识合并后使用（不是覆盖），只保存在本机 `~/.ncm/gui.json`。
  它等同于账号凭证，别分享、别贴聊天记录。
- **标签与封面**：MP3 写 ID3v2.3 + APIC 封面，FLAC 写 Vorbis Comment + PICTURE，中文正常。

## 页签二：NCM 解码

把本地的 `.ncm` 解码/转码成通用格式。**不重写解码算法**，而是驱动已有的 `NCMDecoder.exe`。

> **`NCMDecoder.exe` 是外部独立程序，这个便携包里没有附带。**
> 没有解码器时，下载页照常可用，解码页会明确提示「未找到解码器」，不会静默失败。

- 添加方式：按钮选择，或直接把文件/文件夹拖进列表（需要 `tkinterdnd2`）。
- **输出格式**：内置 9 种预设，下拉框也可直接键入扩展名（如 `m4a`）。
- **码率**：仅对有损格式生效；选无损/保持原格式时输入框自动禁用。
- **并发**：1–8。实测 24 个文件：串行 7.7s → 并发 4 用 2.2s → 并发 8 用 1.2s。
- **解码器路径**：按「设置里填的路径 → 本文件夹 → 本文件夹的 `dist\` → 同级 `dist\` → PATH」顺序自动探测；都找不到就在「设置…」→「解码」里手动指定，或把 exe 放进本文件夹。

## 界面结构（2026-09-19 重做）

主界面原来把「每次都要操作的」和「配一次就不动的」混在一起，铺了 4 行 19 个按钮，
把日志区挤到只剩 8px —— 而日志恰恰是排错时最需要的。已把设置全部收进「设置…」对话框：

| 指标 | 重做前 | 重做后 |
| --- | --- | --- |
| 日志区高度 | **8px**（几乎不可见） | **181px** |
| 下载页控件数 | 72 | 37 |
| 下载页按钮/勾选 | 19 | 9 |

主界面现在只有流程本身，按 ①②③④ 分步：

```
① 添加下载源   多行输入 + 解析/导入/清空 + 关键词搜索
② 下载队列     歌曲列表（含来源列）
③ 操作与进度   开始/停止/重试失败/打开目录/设置 + 双进度条
④ 日志         占满剩余空间
─────────────────────────────────────────────
状态栏:  音乐库目录   音质   登录状态       拖放可用
```

设置对话框（「设置…」按钮）分「下载 / 解码」两页，涵盖账号、目录、音质、命名分类、
歌词选项、解码器路径与默认参数。非模态，改完关窗即生效。

**登录状态用「登记制」显示。** 状态本来只写在一个标签上，但设置对话框关掉后那个控件
就销毁了，再往里写会抛 TclError。改成 `register_login_label()` / `unregister_login_label()`：
状态栏和对话框都登记，谁关闭谁注销，写入时自动跳过已失效的控件。解码器状态同理。

**状态栏必须比笔记本先 pack，且 `side='bottom'`。** 实测两个标签页的请求高度是 909px，
而默认窗口只有 880px：原来 `nb.pack(expand=True)` 写在状态栏之前，空间不够时 pack 把
最后登记的控件挤成 0 高 —— 状态栏 `mapped=0`，音乐库/音质/登录状态平时完全不显示，
而且日志区看着只是"矮了一点"，很容易当成正常。现在状态栏先 pack 并贴底，
笔记本吸收不足（838px）。

**次要文字颜色不再写死。** 说明文字、登录状态这些原来统一用 `#5f6368`，那是给白底设计的
灰，在深色界面（系统把控件底色给成近黑时）对比度只有 3.5:1，实测截图里几乎糊成一片。
现在由 `gui_common` 按 `GetSysColor(COLOR_BTNFACE)` 判断深浅，给 `C_MUTED/C_INFO/C_OK/C_WARN/C_BAD`
五套语义色（深色下 muted 提到 9:1），浅色主题沿用原值。

## 视觉层（gui_theme.py）

外观集中在一个模块里，`MainApp._build_style()` 在创建任何控件之前调一次 `apply(root, style)`。
要点：

- **两组角色色**（窗口底 / 浮面 / 文字 / 次要 / 边框 / 强调 / 选中 / 进度槽），按 `DARK_UI` 选一套，
  所以同一份代码在浅色系统上也是正常样子，不是"只在深色下能看"。
- **主次分明**：`Primary.TButton`（浅蓝底 + 深字）只给「开始下载」「开始解码」，其余按钮一律扁平灰面。
- **分区标题加粗**（`TLabelframe.Label`），① ② ③ ④ 和正文拉开一级；字体统一 Microsoft YaHei UI 9，日志用 Consolas。
- **列表表头**改成扁平 + 次要色加粗，行高 26；进度条 14px 纯色，去掉 vista 默认的渐变。
- 做不了的就不硬做：Vista 主题下 Treeview 无法隔行换色（要逐行打 tag，代价不值），滚动条也只调了配色。
- **横向不顶出**：粘贴下载与关键词搜索拆成两行（同一行全是固定宽度控件时，换个主题或
  字号变大就会把「搜索」按钮挤出窗口，实测过）；搜索框改成 `expand` 吃剩余宽度；
  解码页的提示文字也相应缩短。
- **输入区占位提示**是盖在文本框上的标签，不往框里塞示例文字 —— 后者每次读取都得先判断
  "这行是用户粘的还是我自己写的"，早晚会漏。空框显示、有内容隐藏，`清空` / `导入` 后自动刷新。
- **识别摘要移到按钮行右侧**，出现「无法识别」的行时整条转成提醒色；它不再和静态提示共用一个标签
  （原来一输入就覆盖掉提示，清空后提示也不回来了）。
- 默认窗口从 `1140x880` 提到 `1140x960`：880 下两个标签页请求 909px，日志区会被压到只剩两三行。
  同时把列表从 9/10 行降到 6/7 行、日志从 9/8 行提到 11/10 行。
  改完实测笔记本分配 925 / 请求 829，四段流程 + 状态栏都完整可见。

## 两个踩过的加密坑（维护时注意）

**① Chromium 的「域绑定哈希」前缀。** 新版 Chromium 在 Cookie 密文的明文**前面加了 32 字节**
的域绑定哈希（防止 Cookie 被复制到别处使用）。直接把它当 Cookie 值用，现象非常迷惑：

```
解密后长度 865（真实值 834），前 31 个字符是乱码，尾部却和真实值完全一致
```

GCM 校验是**通过**的——密文没错，错的是没剥这个前缀。而且它解出来是乱码后再用
`decode('utf-8','replace')` 会得到 U+FFFD，塞进 HTTP 头时 requests 直接抛
`'latin-1' codec can't encode`。已在 `_strip_binding()` 里按「前 32 字节非 ASCII 且其后是 ASCII」
保守剥离。

**② Cookie 值必须校验后才能用。** 上面那次事故的教训：拿到 Cookie 后先用
`cookie_is_usable()` 检查（能否 latin-1 编码 + 含 MUSIC_U），坏值绝不落盘 ——
否则应用会带着一个坏 Cookie 启动，所有请求都失败还看不出原因。

## 从其他开源项目借鉴并融合的能力

调研了 GitHub 上的相关项目后，吸收了以下几项（标注了出处）：

| 能力 | 出处 | 说明 |
| --- | --- | --- |
| **歌词下载 + 内嵌** | [toki-plus/netease-downloader](https://github.com/toki-plus/netease-downloader) | 接口 `interface3.music.163.com/api/song/lyric`。存同名 `.lrc`，同时写进标签（MP3→USLT / FLAC→LYRICS），翻译按时间戳与原文合并 |
| **关键词搜索** | 同上（`/api/cloudsearch/pc`） | 以前只能粘链接/ID，现在可以直接搜歌名歌手。搜索结果字段是新版 `ar/al` 结构，做了归一化 |
| **杜比全景声档位** | 同上（`QualityLevel` 枚举） | 我们原来漏了 `dolby` 这档 |
| **断点续传** | 同上（`file_size` / `current_size` 比对） | `.part` 存在时发 `Range` 从断点继续；服务器不支持则自动退回全量 |
| **文件名截断** | 同上（`_sanitize_filename`） | 原来不截断，'歌手 - 歌名' 拼长了会直接写文件失败；现截到 180 字符 |

没有采纳的，以及原因：

- **刷歌 / 每日任务**（[chaunsin/netease-cloud-music](https://github.com/chaunsin/netease-cloud-music)）——该项目自己标注"风控极为严格，存在较高封号风险，不建议使用"
- **手机号 / 短信登录**——同上，风控拦截，该项目已标记为不可用
- **CookieCloud 同步**——跨设备同步 Cookie，本地单机用不上
- **灰歌解锁类功能**——把没有授权给你的内容从别处匹配过来，这属于绕过授权，不是取长补短的范围
- **更现代的 eapi 端点**（`interface3` + `NeteaseMusicDesktop` UA）——我们的 weapi 目前工作正常，没有充分理由去动能跑的东西

## 实测结论（2026-09-19）

真实账号、真实付费曲目、无损档的端到端验证结果：

| 曲目 | 大小 | 时长 | 采样率 | 位深 | 封面 | 标签 |
| --- | --- | --- | --- | --- | --- | --- |
| 海阔天空 / Beyond | 31.1 MB | 326.0s | 44100 Hz | 16 bit | 1 | ✓ |
| 疯狂的阳光 / 张悬 | 23.2 MB | 235.1s | 44100 Hz | 16 bit | 1 | ✓ |

**付费曲目（fee=1）+ 无损 FLAC 可以正常下载**（用会员账号验证，具体账号信息不在本文档里记录）。

### 修掉的一个严重 Bug：错误的 Host 头

上游 `ncm/constants.py` 在请求头里硬编码了 `'Host': 'music.163.com'`。对 API 调用没问题
（requests 本来就会按 URL 自动填 Host），**但音频和封面地址在 `m801.music.126.net` 这类 CDN 上**——
带着 `music.163.com` 的 Host 去请求，CDN 会以 HTTP 200 返回 gzip 过的
`{"code":404,"message":"接口未找到！"}`，正好 43 字节。

现象是**「下载成功」但文件只有几十字节**。上游 CLI 用裸 `requests.get`（不带 session 头）所以没暴露，
GUI 复用 session 下载就会踩上。已在 `gui_common` 里移除该头。

同时给 `_stream_to_file` 加了内容校验：响应 `Content-Type` 是 json/text/html 就直接报错，
不再把错误页当音频写进音乐库——这类问题以后会**响亮地失败**而不是静默产出垃圾文件。

## 实现上的几个取舍

**每个文件一个子进程，并发由 Python 控制。** 没有用解码器自带的 `-c`，因为那样拿不到单文件状态、也无法单独取消。代价是有进程启动开销，好处是每首的状态、失败原因、取消都能精确到行。

**每个任务先写到自己的临时子目录，成功后再原子移入音乐库。** 解码器内部按「目标文件已存在就加 (1)(2)」去重，多进程并发时会同时选中同一个名字而撞车（报 `1003 文件正由另一进程使用`）。各写各的临时目录后，这个竞态从根上消失了。

**取消是安全的。** 中途终止留下的半成品只存在于临时目录，随任务一起删除，不会在音乐库里留下损坏文件。实测取消 30 个任务后，磁盘文件数与「完成」计数严格一致。

**已完成的不会因为随后点了停止而被误标为取消。** 先看退出码与 `[OK]` 行，再看停止标志。

**拖放路径不能用 `tk.splitlist()`。** 它是 Tcl 列表解析，会把 Windows 路径的反斜杠当转义符吃掉（`D:\plain\c.ncm` → `D:plainc.ncm`）。已改为手工按 DND_FILES 格式解析。

**重复内容会自动跳过。** 成品移入音乐库前先和同名文件比对（大小 + 首尾各 1MB）；
内容一致就判为「已存在」，只留一份。整目录重解一遍不会堆出 `X (1).mp3`、`X (2).mp3`…；
内容确实不同（比如换了码率、换了格式）才退让成 `(n)` 命名。40 个字节相同的副本实测是 1 个落盘 + 39 个跳过。

**解码进行中不能改队列。** 行号是结果回填的依据，中途增删会让状态错位到别的文件上，
所以运行期间「添加/移除/清空」按钮会禁用，拖放也会被拒绝。

**输入都做了兜底。** 并发数输入框允许任意键入，而 `IntVar.get()` 遇到非数字会抛
`TclError`——现在会纠正回 1–8 的合法值再回写显示。窗口位置记忆也会先校验是否仍在屏幕内，
换过显示器不会出现"启动了但看不见"。

**空闲时降频轮询。** 有任务时 60ms 一次，空闲时降到 400ms，实测空闲 2 秒内只唤醒 4 次
（原来固定 80ms，约 25 次）。日志控件限制在 1500 行，长时间运行不会越用越卡。

**维护注意：启动用的 `.bat` 必须是 CRLF。** cmd.exe 读 LF-only 的批处理会吃掉每行开头的字符，
表现为双击「没反应」—— 报错长这样：`'xist' 不是内部或外部命令`（`if not exist` 被切）、
`'ythonw.exe' 不是内部或外部命令`（`pythonw.exe` 被切）。程序本身完全正常，日志里一条记录都不会有，
因为 Python 根本没被拉起来。两个启动脚本现在都是 CRLF，并且开头加了 `chcp 65001 >nul`
让里面的中文提示在 GBK 控制台下不乱码。**用编辑器改完 .bat 记得确认行尾仍是 CRLF。**

**维护注意：`python\` 里不要留 editable 安装。** 之前 `site-packages` 里带着一个
`__editable__.netease_cloud_music_dl-0.3.0.pth`，它的 finder 把 `ncm` 硬编码指向开发机上的
仓库目录。开发机上包内 `ncm\` 会被外部目录悄悄顶掉，「便携包里的代码」和「实际运行的代码」
就不是同一份了。现已删除，`ncm` 只由包内 `ncm\` 提供（脚本目录天然在 `sys.path` 上）。

端到端验证脚本（真实账号跑付费曲目下载并校验标签/封面）是开发期工具，不随便携包分发。

## 运行性能（2026-10-07 实测）

先量再改，改完复测。数据都是这台机器上的内置运行时跑的：

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 双击到窗口出现 | 0.67s | **0.36s** |
| `import ncm_gui` | 511ms | 114~180ms |
| 3000 行日志上屏（走队列，一次 drain） | 2900ms | **5ms** |
| 空闲 5 秒的轮询唤醒 | ~25 次 | 11 次（CPU 0%） |
| 工作集 | 61 MB | 46 MB |
| `_fill_tree(1000 首)` / `parse_target(2000 行)` | 4.6ms / 1.5ms | 未动，本来就快 |

三处改动：

1. **日志批量上屏**。逐行 `append_log` 里 93% 的耗时是每行一次 `see('end')` 触发的滚动重绘
   （单测：3000 次 `insert` 2ms，3000 次 `see` 1155ms）。现在 `append_log` 接受一批行，
   两个标签页的 `_drain` 把队列里连续的 `log` 合并成一次上屏 + 一次落盘；
   遇到非日志消息先 flush，保证日志和其它更新的先后顺序不变。
   `log_file_many` 顺带把逐行 `open` 文件改成一批一次。
2. **重依赖挪出顶层**。`requests`(+urllib3) 247ms、`ncm.file_util`(mutagen+PIL) 57ms，
   而它们只在三个 `requests.Session()`、一个 `CloudApi()`、一个 `resize_img()` 里用到，
   全部改成函数内导入 —— 开机不付这笔钱，第一次解析时多等几十毫秒。
3. **空闲轮询降频**（上一轮做的）：`BUSY_POLL_MS/IDLE_POLL_MS` 提到 `gui_common` 统一，
   主循环从固定 200ms 改成有活 60ms / 空闲 400ms。

**试过但没采纳**：把 `.pyc` 预置进包里。实测只省 ~130ms（一次性），代价是 +9MB、570 个文件，
还会连带编进 `Cryptodome.SelfTest` 这种测试套件，不值。改完源码后如果在意首启速度，
自己跑一次 `python\python.exe -m compileall .` 即可，Python 按 mtime+size 自动失效，不会读到旧字节码。
